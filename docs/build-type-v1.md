# Tailor build type v1

Build type URI:
`https://github.com/enverbisevac/tailor/blob/main/docs/build-type-v1.md`

Tailor builds a container from a curated input snapshot using a generated
Dockerfile, scans source inputs and pinned bases, builds a temporary image,
checks the assembled runtime, scans that exact Docker image ID, and runs any
requested workload check before promoting the same ID to the requested tag.
With `--attest`, OCI evidence export must also succeed before promotion.

## Lock format

`tailor.lock` uses schema version 1. It records the generator version, normalized
relative input paths, target Linux platform, runtime/builder digests, entrypoint,
explicit commands/libraries, source-discovery inputs, included-file mappings,
and requested smoke/attestation policy. Files record SHA-256, byte length and
permission bits; native files record runtime destination, SHA-256, package owner
and package version. The generated Dockerfile has a separate SHA-256.

File inventories and declarations are sorted for stable serialization. Native
cache keys depend on runtime content and package identity, so relocating an
otherwise identical sysroot does not change the plan. The sysroot's host path
is not locked; its resolved runtime content is. `--source` inputs are staged,
hashed and scanned as well. The native closure is checked again against staged
artifact/source bytes to detect changes during resolution.

`--locked` compares the current staged plan with the saved plan before scanner
detection, Docker operations or vulnerability scans. It never updates the lock.
The CLI still requires the same build options; it does not execute commands read
from a lockfile. Unknown/malformed schema, changed inputs, modes, platform,
dependencies, generator output or policy fail verification. A fresh vulnerability
scan remains mandatory; advisory databases and scanner choice are not frozen.

Locking JAR/Node/Python inputs requires an explicit target platform. ELF targets
can be inferred from the executable. Foreign-platform runtime probes and smoke
tests require suitable emulation on the Docker host.

## Workload checks

`--smoke-command` supplies a JSON argv array, run directly inside the image with
the entrypoint overridden. Exit status zero passes. `--smoke-http` starts the
normal entrypoint and requests the supplied path/port using a digest-pinned curl
image. The probe shares only the application's offline network namespace;
neither container has external network access, host mounts or a published port.
The helper image digest is part of an HTTP lock policy and provenance inputs.

Containers run as UID/GID 65532 with a read-only root filesystem, dropped
capabilities, no new privileges, resource limits and bounded temporary storage.
Tailor polls detached container state against a monotonic deadline, then removes
the containers on success or failure. HTTP redirects do not pass. The timeout
applies to the workload; tool/image setup and Docker availability have separate
limits. Success is a bounded workload observation, not a complete runtime proof.
Omitting smoke flags records `not_requested` rather than a successful test.

## Evidence and subjects

`--attest` requires Syft and Skopeo on PATH. It exports the scanned Docker ID,
detects Docker versus OCI archive format, and produces an OCI layout containing
the runnable image and two OCI 1.1 subject manifests:

- `sbom`: `application/vnd.cyclonedx+json` generated by Syft.
- `provenance`: `application/vnd.in-toto+json`, an in-toto Statement v1 with
  `https://slsa.dev/provenance/v1` as its predicate type.

Both subjects identify the exported image manifest by SHA-256. Docker engines
can identify images using config, manifest or index digests. Evidence retains
and verifies the descriptor chain from the scanned Docker ID to the original
config. Config bytes are preserved and rootfs diff IDs are checked during OCI
conversion. The OCI manifest digest can differ from the Docker ID; the build
report records both without treating them as interchangeable.

Provenance external parameters are the lock configuration; internal parameters
include the Dockerfile hash. Resolved dependencies include input/native file
hashes, bases and any HTTP probe image. Run details identify Tailor and tool
versions, the invocation, lock digest and build-report digest. The report
records scanner identity, passed vulnerability gates, smoke outcome, actual
platform and times. The export directory includes the plan, CycloneDX JSON,
provenance JSON, build report and `oci/` layout. Failed exports retain
`incomplete.json` for diagnosis and cannot promote the Docker tag.

This is unsigned, locally generated provenance. It does not establish an
authenticated builder identity, a SLSA assurance level, hermeticity or
byte-for-byte reproducible images. Package installers, timestamps, host tools
and compression can still affect output bytes. No registry push is performed.
OCI-aware tools can copy the image and its referrers when publishing later.
